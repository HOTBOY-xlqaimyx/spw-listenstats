# 测试与验证

三层验证，各自覆盖什么、怎么跑。**改完代码后至少跑第 1 层**。

## 第 1 层：纯逻辑自测（默认必跑）

```bash
./gradlew selftest          # 或 NAS: docker compose run --rm builder
```

- **97 项断言**，注入假时钟（`FakeClock`），不依赖宿主
- 覆盖：JSON 编解码与非法输入、存储往返/损坏恢复/上限淘汰、
  10 个播放场景（正常、seek、暂停、空闲阈值、切歌、短会话丢弃、checkpoint、单曲循环、倍速、tick 风暴）、
  未知曲目桶（开/关）与其边界、上报四条路径（成功/失败/定时/仅退出）、队列上限、诊断模块、配置描述不泄露令牌
- 源码在 `src/main/kotlin/.../selftest/SelfTest.kt`，**不进插件包**（`jar` 任务里排除）

## 第 2 层：假宿主机集成测试（可选，`--with-hostsim`）

```bash
cd /vol2/1000/docker/spwbuild && bash release.sh --with-hostsim
# 或单独: docker compose run --rm hostsim
```

- **114 项断言**，用**真实 PF4J** 加载**最终交付的那个 zip**（不是源码）
- 覆盖：描述符解析、扩展点发现、`PluginContext` 注入、start/stop/停用再启用、配置页 4 个按钮按全限定名反射调用、
  上报四条路径、宿主重启后继续累计、崩溃未 stop 时定时落盘、并发回调风暴、**类引用审计**（证明零第三方依赖）
- 为什么可选：跑一轮约 3 分钟；真机验证已经跑通后边际价值下降。**怀疑"打包/加载/清单"问题时优先跑它**
- 注意：它必须**按真实 1 秒节奏**喂 tick（引擎把位置增量与墙钟增量取小），所以不能靠紧循环加速

## 第 3 层：真实宿主（用户真机 + 日志回传）

- Linux 版：只做**可行性验证**（能加载/能 start/扩展点实例化），播放级被所有权校验阻塞，不做规避
- Windows 版：用户实测 + 发 `listenstats.log` 给我分析 —— **这是唯一能验证真实播放链路的方式**
- 分析入口：日志里的诊断块（环境/配置/运行时探测）+ `回调首次触发` + `记录会话` + `已落盘`

## 发布前检查清单

1. `selftest` 全绿
2. 版本号已递增（见 CHANGELOG 的发版清单）
3. 跑 `release.sh`，确认产物 sha256 与大小
4. 快速通道已同步，链接与哈希已交付用户

## 历史教训（都是真踩过的）

| 问题 | 只有哪一层能发现 |
|---|---|
| 外层 zip 清单没写 `Plugin-*` → 宿主拒载 | 第 2 层（包结构自检发现不了） |
| `java.net.http` 缺失 → 插件初始化崩溃 | **第 3 层**（真机才暴露） |
| 时长虚增（倍速/tick 风暴） | 第 1 层（假时钟）+ 第 2 层（并发场景） |
| 自测写错期望值（如"首个 tick 只开会话不累加"） | 第 1 层跑起来才发现 |
