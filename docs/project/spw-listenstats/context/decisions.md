## 2026-09-22｜查缺补漏（0.9.4 / 0.9.5）：修 2 个真 bug + 4 处缺口

**方法**：按「代码 → 数据 → 文档 → 交付」四层逐层过，凡是有断言/实测能证明的都当场验。

**代码层（真 bug）**
1. `SessionLog.load()` 原来把整段循环包在一个 `runCatching` 里 —— **一行 JSON 损坏会让后面所有会话历史都读不进来**。
   改为逐行容错 + 告警「有 N 行无法解析」。
2. `SessionLog.append()` 原来每条都**整份重写**（2000 条 ≈ 500 KB／每首歌一次）。改为正常路径只追加一行（≈250 B），
   只有超上限裁剪时才整份重写。
3. 删掉死代码 `ReportExport.exportSnapshot()`（无调用方）。

**数据/可观测层（缺口）**
4. 诊断块看不到本地报告状态 → 补「本地报告: 开关 / 目录 / 最近刷新 / 待刷新」与「会话历史: N 条 + 路径」。
5. 诊断的「配置原始值」清单是硬编码的，0.9.x 新增的 `local.enabled` / `local.dir` / `report.pageUrl`
   **一个都没登记**（排障时恰好看不见新配置）→ 收敛成单一来源 `ConfigKeys.ALL`，
   并加自测 `testConfigKeysMatchPreferences`：**配置页声明的键必须与代码清单完全一致**，以后忘登记会被拦住。

**交付层（缺口）**
6. `release.sh` 里 hand-edit `docker-compose.yml` 的 hostsim zip 参数**漏过一次**（0.9.5 时还停在 0.9.4）→
   改成脚本自动从 `dist/` 取最新产物同步（已用 0.9.3 → 0.9.5 实测验证）。
7. 构建/发版脚本此前只存在于宿主 → 纳入工作区 `spwbuild-ops/`（含部署命令；`docker-compose.yml` 故意不留副本，
   避免两份真相）。

**展示层**
8. 报告页「最近播放」未标注长曲目的「分段」（同一首 5 分钟一截会看着像重复）→ v0.4.1 加标注与说明，
   有未归因时段时也一并说明。

**文档层**：README 新增「本地报告（默认形态）」整节 + 数据文件表补 `sessions.jsonl`/`config.json` + 清零与搬迁说明；
`ARCHITECTURE.md` 补本地报告数据流与「输出形态（本地 vs 在线）」对照表；`RELEASE.md` 补「改了报告页要多跑一步」。

**验证**：`selftest` 205 → **210 项**；两处页面改动（分段标注 / 未归因提示）都用 CDP 实测；
四通道哈希一致；chromium 用完即关。

## 2026-09-22｜架构口径调整：本地是默认形态，NAS/服务端是可选扩展（0.9.0）

**用户原话**：*「解绑要更彻底……不叫离线报告，默认就是本地，nas和服务器是扩展」*。
**含义**：此前把"本地导出"当成备份功能（要手动点、落在数据目录、只是快照）。
现在反过来 —— **本地报告是插件一直维护的主形态**，上报与在线页是锦上添花。
**落地**：
- `local.enabled`（默认开）+ **自动刷新**：启动 / 每次会话结算后（tick 节流 ≤30s）/ 停止时，覆盖写同一个文件；
- 落点 `我的文档\SPW听歌统计\ListenStats-本地报告.html`（探测 Documents → OneDrive\Documents → Desktop → 主目录），`local.dir` 可指向同步盘或 SMB；
- 新增**本地会话历史** `sessions.jsonl`（滚动 2000 条）→ 本地报告与在线页都有「最近播放」逐条明细；
- 数据即文件：拷走数据目录 = 完成搬迁（`listenstats.json` + `sessions.jsonl` + `report-queue.json`）。
**验收**：本地报告样本放在**没有 report-data.json 的目录**里仍能完整渲染（证明零依赖）；
selftest 200 项；线上页与本地页同一份模板（v0.3.0）。

## 2026-09-22｜易用化（0.8.0 + 报告页 v0.2.0）：能从"能用"到"顺手"，并且能脱离 NAS

**用户点的四项**：报告页时间范围切换 + 数据新鲜度提示、手机扫码二维码、曲目榜搜索/展开全部、插件「打开报告页」按钮。
**用户补的一条（更重要）**：*数据本地持久化、解绑 NAS 和服务器*。
**做法**：
- **离线自包含报告**：报告页模板作为资源打进插件（`classes/web/report.html`），「导出离线报告」按钮用**与接收端同一套口径**
  聚合本地 `listenstats.json`，把数据内联进模板，产出一个单文件 HTML —— 双击即看，不联网、不需要 NAS。
  这是"解绑"的关键：在线看是 NAS 的事，**离线快照是插件自己的事**。
- 报告页线上/离线**同一份文件**（v0.2.0），离线模式自动隐藏二维码、页脚标注「离线快照 · 导出于 …」。
- 二维码用 python-qrcode 在**部署期**生成内联 SVG（页面仍零外部依赖），并用 OpenCV 解码验证真能扫出来，
  避免"看起来像二维码但扫不出来"。
**边界**：离线报告只有聚合视图（总量/每日/艺人/曲目）—— 逐条会话明细从来不在插件本地留存（只在接收端的 jsonl 里）。

## 2026-09-22｜决策 1 定案：无法归因的播放改成「能归因就归因，归不了才记未归因」（0.7.0）

**背景**：曲目身份只来自 `onBeforeLoadLyrics`，而插件启动时已在播的那首宿主**不会补调**。
真机 5 天日志里有 6 次「收到位置回调但尚无曲目信息」，位置已到 111.7s / 260.8s / 139.7s / 115.7s / 29.6s / 0s —— 这段时长此前全丢。
原来的开关只有两个粗糙选项：丢掉，或记成一条巨大的「未知曲目」污染榜单。
**决策**（0.7.0）三件事一起做：
① **默认改成计**（关掉才是丢弃）；
② **迟到归因**：位置先到时把时长挂在「占位会话」，曲目信息一到就归因给这首曲目；
③ **未归因独立成字段** `totals.unattributedSeconds`（计入总量/每日，不进曲目表），报告页做成脚注。
**安全阀**：占位期间位置回跳（很可能已换歌）→ 不认领，避免把 A 的时长算到 B 头上。
**验证**：selftest 164 项（迟到归因 / 回跳不认领 / 未归因独立记账 / 落盘往返 / 上报字段 / 默认值）。
**基线（用户 2026-09-22 明确）**：**历史未归因不补算、不追溯**，计数器从装上 0.7.0 那一刻起从 0 开始。
核实过：本地 `listenstats.json` 无哨兵条目、`totals` 里也没有该字段（读取即 0）；接收端 25 个历史批次里
0 条带 `unattributedSeconds`、0 条哨兵会话/曲目 —— 所以不存在需要清理或补算的历史值。

## 2026-09-22｜容器更名：ds5db → staticweb（按用途，而非按最早的站点命名）

**背景**：`ds5db` 只是个裸 `nginx:alpine`（8123→80，挂 `./web` 只读），当年为 DualSense 库而建；
现在 `web/` 里已经托管了**所有静态站**（DS5 库在根、听歌报告页 `/spw-report/`、架构图 `/spw-arch/`、快速通道 `/downloads/`）。
**决策**：目录 + compose 服务名 + 容器名统一改为 **`staticweb`**（目录名 = 项目名 = 容器名，维持既有约定）。
**边界分析**（改名前的依赖盘点）：
- 容器名：**零依赖** —— `ds5db_default` 网络上只有它自己，没有容器/脚本按名字访问它。
- 目录路径：**有硬耦合** —— DS5 管线脚本 `app/**` 57 处、周更 cron、`publish.sh`、`spw-receiver` 挂载、11 个技能文件、8 个 DSH 文档、记忆库。
- URL/端口：**零影响** —— 8123 不变，报告页/下载通道/DS5 站点/架构图链接都不用改。
- 备份：`backup_nas.sh` 整树备 `/vol2/1000/docker`，无 ds5db 专属 exclude → 不受影响。
**执行**：备份到 `/vol3/1000/backup/rename-ds5db-20260922-012400/` → `mv` 目录 → 全树 sed 路径（22 个文件，残留 0）
→ 重写 compose（服务/容器名 staticweb）→ 停旧容器、删旧网络 `ds5db_default`、`compose up -d` 起 `staticweb`（停机约 5 秒）
→ 同步 cron / publish.sh / spw-receiver 挂载与重建 → 技能库 11 文件 → 工作区 8 文件。
**验证**：6 个站点/接口全部 200（`/`、`/data.json`、`/spw-report/`、`report-data.json`、`/spw-arch/`、`/downloads/*.zip`）；
接收端 `--force-recreate` 后仍能写入新路径下的 `report-data.json`（01:26 复验）。
**回滚**：`mv /vol2/1000/docker/staticweb /vol2/1000/docker/ds5db` + 从备份目录恢复被 sed 的文件 + 重建容器。
**附带**：`app/docker-compose.yml` 是过期副本（healthcheck 指向不存在的文件），已加「勿用」说明并改名，真正的编排在上一层。

## 2026-09-22｜上报与「有没有新会话」解耦（0.6.0 / 0.6.1）

**事故**：0.5.0 的 `trackStats` 上线后，真机报告页仍然「数据不对」——曲目榜 15 首、艺人榜 1 人（本地实际 55 首）。
**根因**：上报**只在队列非空时**才发，而 `mode=interval` 下用户装完新版还没听完一首歌 → 队列为空 →
全量摘要（含 `trackStats`）永远发不出去；点「立即上报」还回一句「队列为空」。
**决策**：把「有没有新会话」与「该不该上报」解耦。
① 落盘记账 `reportState.summarySignature/sentVersion`；
② **版本号变了**或**本地统计变了**，即使队列为空也发一份 `summaryOnly: true` 的纯摘要（发成功才记账，不重复发）；
③ 触发点全接：启动补发、定时、退出、**手动按钮改为强制发送**；
④ 定时任务里**先去重再调用**（`pending>0 || 摘要过期`），否则 `lastFlushAt` 只在成功时更新 → 每 5 秒刷一行日志（0.6.1 修）。
**教训**：上报类功能必须问一句「**没有新事件时，状态快照靠什么送达？**」——把快照搭在事件队列上就是这次事故。

## 2026-09-22｜报告页数据源：插件补发全量 trackStats（而不是回补历史会话）

**问题**：报告页要「曲目榜 / 艺人榜」，但 `sessions[]` 只覆盖**开启上报之后**的会话 ——
真机上累计 75 次会话、上报里只有 12 次，榜单会大面积缺失。
**方案对比**：① 让接收端/插件回补历史会话（P7）；② 让插件在上报里带一份**全量逐曲目聚合**。
**决策**：选 ②。插件的本地 `tracks` 本来就是全量累计，`summary` 里加 `trackStats`（降序、≤2000 条、
`trackStatsTotal` 报全量）即可；协议仍是 `spw.listenstats.v1`，**纯增量**，旧接收端忽略未知字段。
**代价**：插件要升到 0.5.0 并重开一次；**收益**：聚合视图一次性完整，P7（历史补发）只剩「逐条会话明细」需要。

## 2026-09-22｜接收端把聚合结果写进静态站目录，页面同源 fetch

**决策**：`spw-receiver` 在每次收到上报后，把聚合结果**原子写入** staticweb 静态站的
`web/spw-report/report-data.json`（容器内挂载为 `/report`），报告页 `fetch('./report-data.json')`。
**放弃的方案**：① 页面跨域 fetch `:8199/api/report`（要 CORS、多一个源）；
② 给 staticweb 的 nginx 加反代（要动别人的应用配置）。
**理由**：符合「静态数据站 = 纯前端 + index.html + fetch(data.json)」的既有约定，零 nginx 改动、零 CORS。
写入用「临时文件 + os.replace」并显式 `chmod 644`（fnOS 挂载卷权限会退化成 000）。

## 2026-09-22｜报告页设计选定：变体 B + 夜间模式

**决策**：报告页采用**变体 B（亮色卡片 / 渐变 Hero）**，并加**夜间模式**。

夜间 `--bg:#0e0f12 / --card:#17181c / --fg:#e9eaf0 / --c1:#8b74ff / --c2:#ff86cd`。
**验证**：Chromium 实拍两套主题 × 桌面/移动，无横向溢出、Top10 渲染正常、切换与记忆双向验证。

## 2026-09-22｜报告页数据源的新认识（P7 降级）

**发现**：插件上报的 `summary` 块是**插件本地全量统计**（totals/daily/tracks），
不一定只含"开启上报之后"的数据 —— 真机上首个批次就带着 13922s/68 会话/45 曲目的全量历史。
**影响**：报告页的**聚合视图**（总时长/每日/曲目榜/艺人榜）**不需要历史补发**即可显示完整历史；
`历史补发`（P7）只在需要**逐条会话明细**（如时间线、最近播放列表）时才有必要 → 优先级下调。

## 2026-09-22｜启动/退出上报做成开关 + 用 JVM 退出钩子补缺口（用户要求）

**背景**：用户要求「退出自动上报」与「启动自动上报」。两者其实已存在（退出上报自 0.1.0 的 `stop()` 收尾；
启动补发自 0.3.0），但真机数据暴露了缺口：**7 次退出只有 1 次走到 PF4J 的 `stop()`**，其余是直接关进程 → 退出上报不执行。
**决策**：① 两者都做成显式开关（`report.onStartup` / `report.onExit`，默认开）；
② 退出上报同时挂 **JVM shutdown hook**（正常关窗退出也会执行），并使用**短超时**（连接 3s / 读取 5s）避免拖住退出；
③ 发送前后各落盘一次。
**已知局限**：任务管理器"结束任务"/SIGKILL 强杀时，shutdown hook 不会执行（操作系统层面限制，无法规避）。

## 2026-09-22｜时间控件从「滑块」改为「档位」（用户反馈）

**决策**：`会话断开阈值` 与 `定时上报间隔` 由 `seekbar` 改为 `list` 档位选择。
**理由**：用户反馈滑块拖不准；实测其 `config.json` 里出现 `intervalMinutes = 4.36278` 这种畸形值，
插件只能取整成 4 分钟，用户意图不可控。
**影响**：档位 = 阈值 15/30/60/120/300 秒；间隔 1/2/5/10/15/30/60 分钟。旧值仍可读（取整），选档位后覆盖。
同时抽出可单测的 `ConfigValues`，兼容 `Number` / `"10"` / `"10 分钟（推荐）"` 三种形态。

## 2026-09-22｜事故：脚本自伤写空 `build.gradle.kts`（已恢复）

**事故**：批量脚本里写了 `open(p, 'w').write(open(p).read().replace(...))` —— `open(p,'w')` 先截断，
随后读取到的是空文件，于是把构建脚本写成了 0 字节并同步进构建容器，构建报 `Task 'selftest' not found`。
**恢复**：从发布前快照 `/tmp/v030.tar.gz`（0.3.0 构建前的完整源码包）取回 `build.gradle.kts`，
复核关键片段（pluginManifest、两个 Jar 任务都写清单、`setReadable`、`selftest` 任务）后设版本为 0.3.1，重新构建通过。
**教训**：任何"读-改-写"必须先读进变量再打开写句柄；批量改文件后要 `grep` 校验，不能只看脚本自报成功。

## 2026-09-17｜假宿主集成测试降级为「可选」

**决策**：`release.sh` 默认只跑「构建 + selftest + 发布」，hostsim 改为 `--with-hostsim` 才跑。
**理由**：用户明确要求"不跑假宿主"；真机验证已经跑通，hostsim 的边际价值下降，而每轮多花约 3 分钟。
**影响**：发版更快；hostsim 仍保留（114 项断言），遇到"怀疑打包/加载"时随手可跑。

## 2026-09-17｜版本从 1.0.x 改走 0.x

**决策**：未正式上线前版本号停留在 `0.x`，当前 `0.1.0` → `0.2.0` → `0.2.1`。
**理由**：用户指出"没有正式上线，版本号从 0.x 开始"。
**影响**：文件名带版本；正式上线时才升 `1.0.0`。

## 2026-09-17｜任何修改都递增版本号 + 每次发版同步快速通道

**决策**：`build.gradle.kts` 的 version 必改；`release.sh` 把产物发布到 HTTP/SMB/DSH 三个通道并清旧版本；
交付时必须附上通道链接与哈希。
**理由**：用户要求「有修改就改版本号」「每次版本变更后添加快速通道」。
**影响**：发版清单固化在 `CHANGELOG.md`；通道只留当前版本，历史留在 `build/dist/`。

## 2026-09-17｜HTTP 实现改用 `java.net.HttpURLConnection`

**决策**：弃用 `java.net.http.HttpClient`；并把「上报器构造失败」隔离，不影响本地统计。
**理由**：真机实测宿主是 jlink 裁剪运行时，**Windows 与 Linux 都没有 `java.net.http` 模块**，
用 HttpClient 会在插件初始化阶段 `NoClassDefFoundError`，把整个插件（含本地统计）打挂。
**影响**：上报只依赖 `java.base`；诊断块新增「宿主运行时探测」行，一眼可辨。

## 2026-09-17｜时长累计取 `min(位置增量, 墙钟增量)`

**决策**：每次 tick 最多累计到"两次回调之间的真实耗时"。
**理由**：只按位置增量隐含"位置增量≈真实耗时"的假设；实测 1 秒内补发 4000 次 tick 会被算成 3300 秒（55 分钟），倍速播放同样线性虚增。
**影响**：倍速播放按真实时间计；假宿主必须按真实 1 秒节奏播放（否则测不出东西）。

## 2026-09-17｜插件 zip 的**两份清单**都写 `Plugin-*`

**决策**：内层 jar 与外层打包 zip 的 manifest 写同一份元数据。
**理由**：PF4J 对目录型插件读的是**解包后顶层**的 `META-INF/MANIFEST.MF`（即外层打包任务的清单）；
官方 README 模板只写内层，真机会得到空描述符并报 `Field 'id' cannot be empty`，插件根本加载不了。
**影响**：假宿主加了"两份清单内容一致"的回归断言。

## 2026-09-17｜「未知曲目」桶默认关闭

**决策**：新增 `stats.countUnknownTrack`，默认 `false`；开启后把无法归因的时间记入 `<unknown>`。
**理由**：宿主不回补"插件加载时已在播"那首的曲目信息（实测每次启动丢一段，一次 112 秒）。
但把这段时间记进一个伪曲目会改变统计语义，属于产品取向 → 实现但默认不改行为，交用户决定。
**影响**：默认行为与 0.2.0 完全一致；用户要"总时长不丢"时打开开关即可。

## 2026-09-17｜零第三方运行时依赖（`isTransitive = false` + 显式 pf4j）

**决策**：`compileOnly(api){isTransitive=false}` + `compileOnly/kapt(pf4j)`，不引 Compose/androidx。
**理由**：dev20 的 API POM 仍以 compile 作用域挂着 Compose + Salt UI（dev15–19 播放界面扩展点的遗留），
传递依赖最终指向只在 Google Maven 的 `androidx.*`，直接依赖会解析失败；而这些类插件一个都用不到。
**影响**：依赖图缩到 1 个构件；类引用审计断言"只引用 JDK / kotlin-stdlib / SPW API"。

## 2026-09-17｜Linux 宿主只做可行性验证，不用于功能测试

**决策**：保留 Linux 版运行环境（解压应用 + `spw-linux-run:24.04` 镜像），但不再用它跑功能测试。
**理由**：用户指示；且播放级验证被宿主的渠道/所有权校验（`This application requires a package identity`）阻塞，
**不做任何规避**（那是正版校验）。
**影响**：功能验证走用户的真机（Windows）+ 日志回传闭环。
